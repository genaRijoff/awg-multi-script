## Быстрый старт

```bash
sudo curl -fsSL https://raw.githubusercontent.com/genaRijoff/awg-multi-script/main/awg2.sh -o /usr/local/bin/awg2 && sudo chmod +x /usr/local/bin/awg2 && sudo awg2
```

Запуск в любой момент:
```bash
sudo awg2
```

История версий — [CHANGELOG.md](CHANGELOG.md).

### Канал обновлений

По умолчанию скрипт обновляется из основного репозитория (`pumbaX/awg-multi-script`) —
это стабильный канал. Ранние сборки живут в бета-репозитории
(`genaRijoff/awg-multi-script`): `sudo awg2` → **8) Обновить скрипт** → **2) Переключиться
на бета-канал**. Выбор сохраняется в `/var/lib/awg2/channel` и переживает обновление;
вернуться на стабильный канал можно там же (если бета-версия окажется новее, обновление
предложит откат). Разовый запуск на бета-канале без сохранения:
`AWG2_UPDATE_CHANNEL=beta sudo -E awg2`.

Канал влияет и на Telegram-бота: установка из пункта 6 берёт его код из того же
репозитория.

## ☁ Warp туннель Cloudflare

Обход блокировки IP сервера в РФ. Когда ТСПУ блокирует IP Hetzner/OVH — заворачиваем выходной трафик через Cloudflare.

```
Клиент РФ → AWG → твой сервер → Cloudflare → интернет
```

SSH и серверный трафик идут напрямую — не через Warp.

**Меню Warp (Туннели и DNS → Warp):**

```
1) Установить wgcf и зарегистрировать Warp
2) Активировать Warp+ (лицензионный ключ)
3) Включить туннель
4) Выключить туннель
5) Перегенерировать профиль
6) Управление клиентами в Warp     ← кто через Warp, кто напрямую
7) Health-check + auto-failover    ← если упал — direct routing
8) Импорт wgcf-profile.conf        ← если регистрация блокируется
9) Поиск рабочего endpoint         ← если 2408 режется DPI
d) Удалить Warp полностью
```

**Где взять Warp+ ключ:**
- 🥈 Приложение **1.1.1.1** → Аккаунт → Ключ

**Если Warp не подключается на РФ хостинге:**
1. `Туннели и DNS → Warp → 8` — импорт готового профиля через Google Cloud Shell
2. `Туннели и DNS → Warp → 9` — автоматический поиск рабочего endpoint
3. Если ничего не помогло — провайдер режет UDP к Cloudflare, нужен другой хостинг

### Версия протокола

При создании сервера (и при перегенерации параметров) выбирается версия AmneziaWG.
Она общая для всего сервера: клиент другой версии не подключится.

| Версия | Что добавляет | Требования |
|---|---|---|
| **2.0** | `Jc/Jmin/Jmax`, `S1-S4`, `H1-H4` + мимикрия `I1-I5` | любой клиент AmneziaWG |
| **3.1** | `HeaderProtectionKey`, `ContentPaddingAddition`, рандомизация таймеров (`RekeyAfterTime`, `RejectAfterTime`, `KeepaliveTimeout`, `MaxHandshakeAttempts`), `PersistentKeepalive` диапазоном, `RandomTrailers` (случайный «хвост» у пакетов рукопожатия — их длина перестаёт быть постоянной) и `DisableCookies` (сервер не отвечает cookie-пакетами) | amneziawg-tools и модуль **v3.1.20260812** или новее — и на сервере, и на клиенте |

> Промежуточная **3.0** из выбора убрана в v0.7.22: 3.1 — это она же плюс
> `RandomTrailers`/`DisableCookies`, а требования к версии tools и модуля почти
> совпадают. Серверы, созданные на 3.0, работают дальше без изменений; при
> перегенерации параметров предлагается 2.0 или 3.1.

Скрипт проверяет установленные компоненты до перезаписи конфигов: если `awg` не знает
ключей выбранной версии, он предупредит, а не оставит сервер лежать.

> `DisableCookies = on` отключает штатную защиту WireGuard от флуда рукопожатиями —
> это плата за то, что в трафике не появляется отдельный тип пакета.

**2) Клиенты**
```
1) Добавить клиента
2) Переименовать клиента
3) Удалить клиента
4) Показать QR клиента
5) Показать конфиг клиента (текст)
6) Создать N клиентов (массово)
7) Срок действия клиента (auto-suspend по истечении)
8) Активность клиентов
9) Экспорт конфигов (zip)
10) Сменить мимикрию у клиента
```

> **Вывод установки компактный.** `apt`, `git`, `make` и `dkms` пишут сотни строк — с
> v0.7.23 они уходят в `/var/log/awg2-install.log`, а на экране остаётся строка на шаг:
> крутилка, пока шаг идёт, и `√ Название (42с)` после. При провале печатается `×` с кодом
> возврата и хвост лога **этого** шага. Процентных полос нет намеренно: ни apt, ни dkms не
> отдают долю сделанного, и рисовать их пришлось бы «на глаз».

**3) Диагностика**
```
1) Проверить домены из пулов (ping)   — с этого сервера
2) Тест DPI мимикрии (захват CPS пакета)
3) DPI со стороны клиента             — команда для вашего устройства
```

Пункты 1 и 2 смотрят с сервера. Пункт 3 ничего не запускает и не ставит — он печатает
готовую команду [dpi-detector](https://github.com/Runnin4ik/dpi-detector) (MIT) для
устройства, с которого вы ходите в VPN, и объясняет, что делать с результатом: рабочий
домен → в «Ввести свой», подмена DNS → DNSCrypt, обрыв после первых десятков килобайт →
это ограничение потока, а не оверхед параметров. Сам туннель AmneziaWG им не
диагностируется: UDP кроме DNS, QUIC и WireGuard он не трогает.

**4) Бекапы** — создать (`~/awg_backup/`) / восстановить.

**5) Туннели и DNS** — Warp туннель Cloudflare, шифрованный DNS, каскад на зарубежный VPS.

**7) Удаление и сброс** — очистить клиентов / удалить всё.

## Профили и мимикрия

При создании сервера (Сервер → 2) выбирается профиль:

| Профиль | Обфускация | Мимикрия I1 |
|---|---|---|
| **AmneziaVPN** | значения официального конфига | по умолчанию нет; по согласию один DNS |
| **Мощный** | широкие диапазоны Jc/S/H | на выбор: без I1 / +I1 / +I1–I5, девять профилей |

**AmneziaVPN** — это буквально параметры официального клиента: `Jc≈4`,
`Jmin≈10`, `Jmax≈50`, `S1..S4` вокруг 86/48/16/12, MTU 1280.

**`H1..H4` от профиля не зависят — только от версии.** На AWG 3.x задан
`HeaderProtectionKey`, то есть заголовок шифруется целиком: подменять под шифром тип
пакета бессмысленно, наблюдателю всё равно видна только шифрограмма. Поэтому на 3.x оба
профиля получают штатные `1/2/3/4` — так же, как это делает сам клиент Amnezia. На AWG
2.0 заголовок открытый, и `1/2/3/4` были бы прямым признаком WireGuard, поэтому там
`H` остаются диапазонами обязательно.

**Мощный** сильнее против анализа трафика, но конфиг заметно длиннее, а на
части маршрутов такой профиль теряет в скорости. Если после него скорость
просела в разы — пересоздайте сервер на профиле «AmneziaVPN» и сравните.

### Запас MTU

Полезная нагрузка `MTU` байт превращается на проводе в:

```
MTU + 16 (заголовок транспортного пакета) + 16 (тег Poly1305)
    + S4 (junk перед транспортным пакетом)
    + верхняя граница ContentPaddingAddition
    + 28 (IPv4 + UDP)
    + случайный хвост RandomTrailers, которого в конфиге не видно
```

При MTU 1320 и широких диапазонах «мощного» профиля это подходит к 1500 вплотную.
Крупные пакеты начинают резаться, а PMTU discovery по UDP работает не везде — наружу
это выглядит **не как обрыв, а как просадка скорости в разы при живом туннеле**.

С v0.7.25 скрипт считает эту сумму последним шагом генерации параметров и, если запаса
меньше 48 байт, показывает расчёт и предлагает снизить MTU. Решение за вами — молча
менять выбранное значение скрипт не станет. На профиле **AmneziaVPN** (MTU 1280,
небольшой `S4`) запас есть, и вопрос не задаётся.

> Значение в `# AWG_PROFILE=` не менялось: «AmneziaVPN» пишется как `lite`,
> «мощный» — как `pro`. Промежуточный `standard` из меню убран в v0.7.22, но у
> серверов, созданных раньше, распознаётся по-прежнему.

Пакеты собирает порт [payloadGen](https://github.com/Sketchystan1/payloadGen): структура,
порядок полей и порядок TLS-расширений (то есть отпечаток JA3/JA4) повторены за
оригиналом. Профиль **TLS убран** — TLS-записи поверх UDP не существует, старое имя
`tls` принимается как алиас на `quic`.

Профили мимикрии (Pro, выбор уровня I1–I5):

- **QUIC** — Initial 1200 Б по RFC 9000 с Chrome-подобным ClientHello внутри. Содержимое
  зашифровано по RFC 9001, поэтому смотреть DPI не на что. Профиль по умолчанию.
- **cURL QUIC** — Initial 1250 Б с отпечатком `curl --http3` и **ECH**: настоящий SNI
  зашифрован (HPKE, RFC 9180), наружу видно только `public_name`.
- **DNS** — запрос c EDNS0 и случайным TXID. Самый компактный профиль: ~34 Б на пакет.
- **STUN** — Binding или TURN Allocate к реальному ICE-провайдеру (Google, Cloudflare,
  Meta, Twilio), с корректным FINGERPRINT по RFC 5389.
- **WebRTC** — связка начала звонка: STUN Binding + DTLS ClientHello + RTP + RTCP.
- **SIP** — OPTIONS / REGISTER / INVITE / 100. Настоящий UDP-протокол, но открытый текст.
- **NTP** — client mode 3, ровно 48 Б.
- **RTP** — медиапоток; без предшествующего сигналинга выглядит вырванным из контекста.
- **SSDP** — M-SEARCH; локальный протокол, наружу ходит редко.

Домен спрашивается **один раз и уходит во все пять пакетов** — настоящий клиент за одно
рукопожатие ходит на один хост.

**Свой домен предлагается первым и почти всегда лучше встроенного пула.** Пул одинаков
у всех, кто ставит эту тулзу, поэтому DPI учится по нему быстрее всего, а недостоверный
домен (мёртвый, заблокированный, не отдающий HTTP/3 при QUIC-профиле) ломает подключение
раньше, чем встают вопросы о скорости. Годится любой живой сайт, куда вы реально ходите
с этого устройства.

> **Автопроверка домена идёт с сервера, а мимикрию разбирает DPI у провайдера клиента.**
> Домен, живой с VPS во Франкфурте, может быть заблокирован или подменён у конкретного
> оператора в РФ — и наоборот. Проверить со стороны клиента `awg2` не может по построению,
> поэтому лучший источник домена — сам клиент. Готовый инструмент для этого:
> [Runnin4ik/dpi-detector](https://github.com/Runnin4ik/dpi-detector) (MIT, запускается у
> вас, не на сервере) — он же покажет TLS 1.2/1.3, подмену DNS, SNI-блокировку и обрыв
> TCP после 14–34 КБ. Берите оттуда домен, который он показал рабочим, и вводите его в
> пункт «Ввести свой».

Встроенный пул — резервный: с v0.7.22 это инфраструктурные хосты с постоянным фоновым
трафиком (`yastatic.net`, `mc.yandex.ru`, `avatars.mds.yandex.net`, `ok.ru`, `st.mycdn.me`,
`vk.ru`, `kinopoisk.ru`, `hh.ru`, `2gis.ru`, `lenta.ru`, `mos.ru`, `citilink.ru`) вместо
списка payloadGen. Пул подбирается под профиль: `quic`/`curl_quic` берут проверенные на
HTTP/3 домены, `sip` — домены SIP-провайдеров. Перед выбором домены проверяются на
доступность. NTP, RTP и SSDP домена не содержат вовсе, а STUN и WebRTC без явного ввода
берут адреса из пула своего ICE-провайдера.

> Если конфиг не проходит у конкретного провайдера, профиль меняется у одного клиента
> без пересоздания: **Клиенты → «Сменить мимикрию у клиента»** или кнопка
> **🎭 Мимикрия** в карточке клиента в боте. I1–I5 живут только в клиентском конфиге,
> поэтому сервер и остальные клиенты не затрагиваются — переподключать их не нужно,
> но самому клиенту нужен новый конфиг.

> Текущий профиль клиента хранится меткой `# mimicry=<профиль>` в его peer-блоке в
> `awg0.conf` и виден в меню и в карточке бота. По самому пакету `I1` профиль не
> определяется: сигнатуры профилей пересекаются. У клиентов, выданных до v0.7.21,
> метки нет — она появится при первой смене профиля.

> CPS-пакеты I1–I5 — это **клиентские** параметры. В серверный `awg0.conf` они не пишутся (там только Jc/Jmin/Jmax/S/H). Разные клиенты могут иметь разную мимикрию на одном сервере.

### Размер CPS-пакетов

I1–I5 уходят перед каждым рукопожатием и пишутся в конфиг чистым hex, поэтому цепочка из
крупных пакетов заметно утяжеляет конфиг:

| Профиль | I1 | Суммарно I1–I5 | Символов в конфиге | QR |
|---|---|---|---|---|
| DNS | 34 Б | ~170 Б | ~370 | да |
| NTP | 48 Б | ~240 Б | ~510 | да |
| STUN | ~130 Б | ~640 Б | ~1300 | да |
| RTP | ~160 Б | ~760 Б | ~1550 | да |
| DTLS | 180 Б | ~900 Б | ~1830 | да |
| SSDP | ~220 Б | ~1.1 КБ | ~2180 | впритык |
| WebRTC | ~510 Б | ~2.4 КБ | ~4900 | нет |
| SIP | ~560 Б | ~2.8 КБ | ~5600 | нет |
| QUIC | 1200 Б | ~6 КБ | ~12000 | нет |
| cURL QUIC | 1250 Б | ~6.3 КБ | ~12500 | нет |

QUIC I1 остаётся 1200 Б намеренно: [RFC 9000 §14.1](https://www.rfc-editor.org/rfc/rfc9000#section-14.1)
требует этого от любой клиентской датаграммы с Initial — сервер обязан отбросить
короткий Initial, а для DPI это готовая аномалия.

Конфиг крупнее ~2800 байт в читаемый QR не помещается — скрипт предупреждает об этом
сразу после генерации и выдаёт конфиг текстом.

С v0.7.22 длину цепочки задаёт **бюджет** (меню «Длина цепочки I1-I5» на уровне «+I1-I5»):
компактная (~1500 символов, по умолчанию), средняя (~3000) или без лимита. Бюджет режет
цепочку **целыми пакетами** — обрезанный пакет это не снимок протокола, а обрубок, по
которому DPI отличает нас быстрее, чем по отсутствию мимикрии. Поэтому сколько пакетов
поместится, зависит от профиля: DNS укладывает все пять в ~440 символов, а один QUIC
Initial занимает ~2400 и выдаётся целиком даже при меньшем бюджете.

Размер, по которому пакет режется на несколько I, задаётся переменной
`AWG_CPS_MTU` (1200–1500, по умолчанию 1280).

### Зависимости генератора

`python3-cryptography` — не обязателен, но без него QUIC Initial уходит **без шифрования**
(содержимое перестаёт быть похожим на шифротекст), а ECH у профиля cURL QUIC отключается.
Генератор в этом случае пишет предупреждение в stderr. Ставится так:
`apt-get install -y python3-cryptography`.

По умолчанию ECHConfig для cURL QUIC генерируется локально: структура расширения от
настоящего ECH неотличима, расшифровать его всё равно некому. `AWG_CPS_ECH_DOH=1`
разрешает сходить за опубликованным ECHConfig домена по DoH — это внешний запрос
к `dns.google`, который в РФ часто недоступен, поэтому он и выключен по умолчанию.

### Совместимость клиентов с цепочкой

Диапазоны `Jc`/`S`/`H` — параметры устройства: они одинаковы у сервера и всех клиентов и
клиентом не сужаются. Отличается между клиентами ровно одно — читают ли они I1–I5:

| Клиент | Цепочка |
|---|---|
| Amnezia VPN / AmneziaWG | читает |
| Linux / OpenWrt (модуль ядра) | читает |
| Keenetic (KeeneticOS 4.x) | движок цепочки по исходникам не установлен, длинная ненадёжна — надёжнее уровень «+I1» и профиль DNS (самый компактный из тех, что содержат домен) |
| **WireSock** (Windows) | **не читает вовсе** — подходит только уровень «Базовый» |

> ⚠️ **WireSock** (форк BoringTun) не поддерживает I1–I5: по документации вендора поля
> «silently ignored». Туннель поднимается, мимикрии в трафике нет, ошибки тоже нет —
> худший вид поломки, тихий. Обфускация `H`/`S`/`Jc` у WireSock работает в полном объёме.

> В v0.7.24 отдельный вопрос «куда поедет конфиг» убран: он влиял только на цепочку, а у
> профиля **AmneziaVPN** её нет вовсе — то есть задавался в каждом сценарии и почти
> всегда ни на что не влиял. Эти же предупреждения теперь стоят в меню «Уровень
> обфускации», где цепочка и выбирается.

> Используются только теги `b`, `r`, `rc`, `rd` — их понимают оба движка
> (`amneziawg-go` и модуль ядра). `<c>` есть только у ядра, `<d>/<ds>/<dz>` — только
> у go, а незнакомый тег отвергается вместе со всем пакетом, а не сам по себе.

## 🔐 Шифрованный DNS (Туннели и DNS → DNS-шифрование)

Все DNS-запросы клиентов идут через DoH (DNS-over-HTTPS) к Cloudflare / Google / Quad9 с проверкой DNSSEC.

```
Клиент → AWG → DNAT iptables → dnscrypt-proxy → DoH → Cloudflare/Google/Quad9
                (порт 53)        (127.0.0.1:5300)        (HTTPS зашифрованно)
```

**Что даёт:**
- Защита от DNS-leak (даже если в конфиге клиента указан 8.8.8.8 — запрос пойдёт через шифрованный канал)
- Провайдер сервера не видит какие домены резолвятся
- DNSSEC защищает от подмены ответов
- No-logging резолверы

**Меню:**
```
1) Включить (установить + настроить)
2) Перезапустить сервис
3) Логи
4) Сменить upstream (Cloudflare / Google / Quad9 / комбинации)
5) Выключить и удалить
```

## 🤖 Telegram бот

Опционально — Telegram бот для управления сервером со смартфона. Добавляешь токен от @BotFather, и бот даёт inline-меню с теми же возможностями что и SSH. Управление полностью кнопками, без команд.

**Что умеет:**
- Список клиентов со статусом (🟢 онлайн / ⚪️ офлайн / 🚫 заблокирован, трафик, маршрут, последний handshake), в два столбца, с пагинацией (◀️ ▶️) — корректно работает при сотнях клиентов
- ↕️ **Сортировка по активным** — кнопка поднимает онлайн-клиентов наверх
- 🚨 **Сигнал при отвале клиента** — добавь `#ping` в заметку клиента, и если такой клиент пропадает из сети (нет handshake более 5 минут), бот шлёт уведомление (имя, IP, заметка, время пропажи). Чтобы не пропустить упавшее резервирование
- Добавить клиента — выбор профиля мимикрии прямо в боте (QUIC / cURL QUIC / DNS / STUN / WebRTC / SIP / NTP / RTP / SSDP / базовый). Длина цепочки ограничена тем же компактным бюджетом, что и в `awg2` (~1500 символов), а домен берётся тот, что выбран при создании сервера — клиенты одного сервера маскируются под один хост
- На сервере с профилем «AmneziaVPN» бот повторяет его поведение: если мимикрия выключена (`# AWG_MIMICRY=none`), клиент от бота тоже идёт без `I1-I5`
- 🎭 **Сменить мимикрию у выданного клиента** — кнопка в карточке (то же, что п.10 меню клиентов в `awg2`): меняются только `I1-I5` этого клиента, в ответ приходит новый `.conf` и QR
- Получить QR-код / .conf файл по любому клиенту (для больших конфигов с I1 QR не помещается — бот автоматически отдаёт `.conf`)
- 📝 **Заметки к клиентам** (произвольный текст; маркер `#ping` включает мониторинг)
- ☁️ **Вкл/выкл WARP для клиента** прямо из карточки — синхронизировано с awg2 (policy-routing через `peers.list`)
- ⏰ **Срок действия клиента** (1ч / 1д / 7д / 30д / своя дата) с auto-suspend по истечении и уведомлением; снятие срока возвращает доступ
- 🌐 **Смена upstream шифрованного DNS** (DNSCrypt: Cloudflare / Google / Cisco / Yandex Safe)
- Переименовать / удалить клиента с подтверждением
- Статус сервера (uptime AmneziaWG, IP и порт, профиль, версия AWG, мимикрия и её домен, сводка по клиентам и трафику), перезапуск интерфейса, резервная копия
- 👮 **Несколько админов** — «Обслуживание → Управление ботом → Админы бота»: одноразовая ссылка-приглашение или добавление по Telegram ID, отзыв доступа в одно нажатие (подробнее ниже)

**Установка:**

Проще всего — через главное меню: `sudo awg2` → **6) Telegram-бот** → Установить.

Или вручную:

```bash
sudo bash -c 'curl -fsSL https://raw.githubusercontent.com/pumbaX/awg-multi-script/main/awg-bot-install.sh -o /tmp/awg-bot-install.sh && bash /tmp/awg-bot-install.sh'
```

В процессе установщик спросит:
1. **Bot Token** — получи у [@BotFather](https://t.me/BotFather): `/newbot` → имя → токен
2. **Telegram ID** — твой ID для авторизации (узнать через [@userinfobot](https://t.me/userinfobot))

После установки бот стартует как systemd-сервис (`awg-bot.service`) и сам поднимается при перезагрузке.

**Канал обновлений (стабильный / бета):**

У бота тот же выбор канала, что и у `awg2`: **стабильный** — основной репозиторий, **бета** — ранние сборки, которые могут быть сырыми.

- В боте: **Управление ботом → ⬆️ Обновить** — там видно текущий канал и кнопка переключения. Переключение меняет только источник кода; чтобы приехала версия из нового канала, нажми «Обновить бота» ещё раз.
- В консоли: `sudo awg-bot` → пункт **8) Канал обновлений**, либо неинтерактивно:

```bash
awg-bot channel               # показать текущий канал и репозиторий
awg-bot channel beta          # переключить на бета
awg-bot channel stable        # вернуться на стабильный
```

Канал хранится в `/etc/awg-bot.conf` строкой `UPDATE_CHANNEL=`, вместе с ним переписывается `REPO_URL=`. Если канал явно не выбран, бот наследует канал `awg2` (`/var/lib/awg2/channel`) — так бот и скрипт не разъезжаются по разным репозиториям. Если задан локальный источник кода (`awg-bot src /путь`), он сильнее канала: обновление берёт код из каталога, о чём бот предупреждает прямо на экране.

**Несколько админов:**

Доступ к боту может быть у нескольких человек. Различаются два уровня:

- **владелец** — ID из `ADMIN_ID` в `/etc/awg-bot.conf` (можно перечислить несколько через запятую: `ADMIN_ID=111,222`). Только владелец правит список админов;
- **приглашённый админ** — добавляется из бота: **Обслуживание → 🤖 Управление ботом → 👮 Админы бота → ➕ Добавить админа**. Два способа:
  - 🔗 **ссылка-приглашение** — одноразовая, живёт 15 минут, сгорает при первом переходе; узнавать чужой ID не нужно;
  - 🆔 **по Telegram ID** — если ID уже известен (человек смотрит его у [@userinfobot](https://t.me/userinfobot)).

Список хранится в `/var/lib/awg-bot/admins.json` (права `0600`), применяется сразу — перезапуск бота не нужен. Отзыв доступа — кнопка «🚫 Отозвать» напротив админа. Любое изменение списка приходит владельцам отдельным сообщением.

Честно о границах:

- приглашённый админ может в боте всё то же, что владелец: клиенты, конфиги с приватными ключами, бэкап, перезапуск сервера, удаление бота. Разница одна — список админов правит только владелец;
- это доступ **к боту**, а не SSH и не `awg2` в консоли;
- владельца из бота снять нельзя — только правкой `/etc/awg-bot.conf` и перезапуском сервиса;
- уведомления бота (офлайн/онлайн по `#ping`, истёкшие клиенты) получают все админы;
- уведомления самого `awg2` (таймер истечения `awg2-expire.timer` в консоли) уходят на один `ADMIN_CHAT_ID` из конфига — приглашённые их не увидят.

**Обновление:** меню **6) Telegram-бот** → Обновить (или пункт 1 в меню установщика, либо `sudo awg-bot` → 2). Свежая версия тянется с GitHub автоматически, токен и chat_id сохраняются. Переход со старого бота — без потери данных (`ADMIN_CHAT_ID` переносится в `ADMIN_ID` автоматически).

**Управление в консоли:**
```bash
sudo awg-bot                        # меню: установка / обновление / статус / логи / удаление
```

**Команды бота:**
- `/start` — главное меню (inline-кнопки)

**Управление сервисом:**
```bash
sudo systemctl status awg-bot       # статус
sudo systemctl restart awg-bot      # перезапуск
sudo journalctl -u awg-bot -f       # живые логи
```

- Проверка H1-H4 sub-квадрантов (12/12 = идеал)
- Security / Stealth / DPI score
- Рекомендации CRIT/HIGH/MED/LOW + пошаговый upgrade path
